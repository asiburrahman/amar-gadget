## Implementation contract

- Explicit marketing consent is separate from account registration and support-message permission. Normalize/bound email input and persist the actual consent version/time. Guest requests never authorize an account/customer operation.
- Use double opt-in through the configured Nodemailer SMTP transport. Pending requests are not active subscriptions. A request receipt does not claim activation, SMTP acceptance does not claim inbox delivery, and provider/configuration failures do not produce a fake subscribed state.
- Confirmation and unsubscribe capabilities use distinct domain-separated HMACs. Confirmation expires after 24 hours and is tied to the current confirmation generation/nonce. Replaced/expired confirmation links cannot reactivate an unsubscribed preference. The unsubscribe capability remains usable across subsequent requests so a recipient can stop mail using an older message.
- Put capabilities in email URL fragments, then require an explicit page action POST. GET navigation/mail scanners do not change consent. Never print tokens or include them in URL queries, response metadata, persistent client storage or public subscriber lists.
- Serialize exact request identities and normalized recipient decisions, preserve durable delivery/retry evidence, bound delivery claims and rate limits, and handle competing requests/crashes without activating an unconfirmed recipient. SMTP itself does not provide exactly-once delivery; uncertain delivery may resend the same confirmation capability/message identity.
- Provide truthful form feedback and real confirmation/unsubscribe pages. Administrative subscription/delivery visibility must remain private, bounded and based on current database authority. Do not invent a campaign/broadcast result or claim hosted SMTP verification from an isolated test transport.
- Rehearse fresh installation and upgrade in isolated local databases; verify SQL, provider boundaries, token privacy/expiry/replay, current roles, frontend failures and compiled HTTP flow. Keep all prior audit tasks, release checks and external SMTP revocation open until their own evidence is complete.

## Persistence and public API checkpoint

Migration 35 (`20261103160000_newsletter_consent`) successfully applied in newly created disposable databases and is **frozen**. It adds normalized unique subscribers, current pending/active/withdrawn preference, consent version/time, confirmation generation/nonce/expiry, stable unsubscribe nonce, immutable event history and durable delivery requests. SQL guards require matching transition/request evidence, refuse orphan events and protect retained delivery/content identities. Original confirmation capabilities cannot reactivate withdrawal or a later confirmation generation. No existing accounts become subscribers through migration.

Actual public services and `/api/newsletter`, `/api/newsletter/confirm`, `/api/newsletter/unsubscribe` POST handlers are implemented. Requests use strict JSON/query/body limits, trusted-ingress IP/hashed-recipient rate limits, durable UUID/content-hash retries and a database recipient cooldown/window. Public request responses contain only their original reference/time, never subscription membership or a capability. GET navigation is not a preference mutation. A provider failure returns unavailable and retains the request without activating consent.

Delivery claims use subscriber-before-request row locks, unique 90-second leases, UTC dates and cumulative attempt evidence. SQL locks are released before SMTP. A live lease excludes a competing claim; expired claims can be recovered and stale completion cannot replace a newer lease. Transport/configuration/rejection failures retain safe codes and exponential retry; exhausted attempts become DEAD. The sweep admits at most five requests and skips withdrawn/replaced/expired pending deliveries. SMTP acceptance records a delivery attempt outcome, not inbox delivery or activation; in-flight messages cannot be recalled by withdrawal and uncertain SMTP outcomes may duplicate a message. Confirmation remains an explicit capability action.

An already-active recipient may request preference-management mail with a current unsubscribe capability, including after signing-key rotation. It does not record another activation or expose membership in the public response. Pending resends reuse a still-valid generation; mail displays its actual UTC expiry rather than promising another 24 hours. Withdrawn/expired preferences need a fresh generation and explicit confirmation. Durable event history is retained throughout.
