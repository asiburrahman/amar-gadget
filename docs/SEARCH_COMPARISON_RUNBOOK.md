# Search and product comparison (AUD-020)

Both header search forms now submit `q` and an optional real category name/slug to `/search`. The optional category field loads bounded suggestions from the existing rate-limited catalog-options endpoint; typing searches further records, with debounced requests and cancellation. It is not a fixed list of invented categories. An unavailable suggestion service shows a retry control; text search still submits independently. Exact category selectors are resolved by the shared catalog resolver.

`/search` validates the same contract as `/products` and redirects valid requests to its canonical listing URL (`q` becomes `search`). Other valid filters and page settings survive. Duplicate/conflicting/malformed query fields render the listing's correction state. The website SearchAction destination therefore works, while all result filtering/counting/paging still uses the shared AUD-019 service. There is no second search database implementation to drift from the header/API contract.

## Selection and live comparison

Product cards, details and category showcases offer the same Compare button. Selection contains **IDs only**, capped at four distinct products. The header links to that exact selection and displays its count. Removing items frees a slot; exceeding the limit shows an actionable message. Public IDs are stored under `amar-gadget-comparison`, version 1. Corrupt/duplicate/overlong persisted data is discarded. Blocked/quota-failed browser storage retains an in-memory selection for the current page session. No identity, price, description or specification snapshot is trusted from browser storage.

The canonical share URL is `/compare?product=ID&product=ID`, preserving selection order. Explicit URL IDs take precedence over a prior saved selection. Opening an empty `/compare` offers a restore link rather than silently replacing the URL; Clear comparison explicitly clears stored state. Remove links work as ordinary navigation even without JavaScript. Changing selections through the UI updates the browser store as well. One-product, empty, unavailable-record, invalid-selection and service-failure states are distinct. Hidden/missing records retain removable selection slots, without revealing their names or details.

The server reads at most four matching approved products belonging to approved sellers. It refreshes prices/discounts/availability directly from SQL and never broadens an invalid selection into a catalog listing. The table uses actual category/brand records and technical specifications, aligns labels case-insensitively and says Not supplied for a missing value. Different categories can be compared; no product is declared better from unrelated or absent specifications. React renders labels/values as text. Prices follow checkout's `discountPrice ?? price` policy. Final checkout still independently validates actual prices and stock.

## Persisted specifications

Migration `20261029100000_product_specifications` adds `Product.specifications`, a non-null JSON array defaulting to `[]`. Existing products preserve their other fields and receive no invented technical data. Apply this migration before deploying this revision; readiness requires it. Back up and follow the normal approved production rollout process. No production database was migrated by this work.

Each item is exactly `{ label, value }`: trimmed plain text, nonempty label up to sixty characters and value up to three hundred, no control characters, at most thirty items and no case-insensitive duplicate labels. Application create/update/approval validation and a PostgreSQL CHECK/function bound this field; direct SQL cannot bypass its structural/length/duplicate guards. Values are seller-supplied facts, not scraped guesses or certifications.

The actual seller add-product form edits these rows and sends them through the same validated upload/publication action, persisting them with the pending product. Administrators can correct existing products through the specifications editor on `/admin/products`; the action rechecks current verified administrator role/session version under the account lock and locks the product before replacing its array. Failed saves keep the edits and show the real failure; success is shown only after commit. Product detail renders the same stored specifications. Broader seller catalog editing remains AUD-031 and is not silently declared finished here.

## Verification and limits

Use a disposable local `audit_*` PostgreSQL database and set TEST_DATABASE_URL before Jest. `npm test -- --runInBand` includes actual SQL comparison/visibility/current-price/admin-authority cases, direct SQL constraint rejection, a new-database migration rehearsal preserving an existing product, actual signed upload/create persistence, form payloads, selection/limit/remove/clear/storage failure and header GET contracts. Provider fixtures and UI mocks are confined to tests. The migration rehearsal creates and drops only its own randomly named, validated local fixture database and requires local CREATE DATABASE permission.

After `npm run build`, `npm run smoke:brands` checks the prepared server's advertised search redirect, comparison table/specifications/visibility, product detail and actual header forms alongside AUD-018/019 regressions. It follows either an HTTP Location or Next's explicit streaming refresh destination, then verifies the real filtered result page. It checks specifications in the actual HTML table and ignores React text-boundary comments when reading visible status text. `npm run smoke:catalog-actions` discovers compiled action metadata without printing the manifest key, logs in, sends real Next Action HTTP requests, and verifies specifications SQL writes plus malformed/revoked-session denial. `npm run smoke:standalone` checks packaged assets, catalog, login/readiness and cookie revocation. Run Jest and native smoke runners sequentially when sharing one database: older checkout tests assert global user-count deltas and are not isolated from a separate concurrent fixture process. Parallel runners require separate disposable databases. These are server HTTP/UI component checks, not an interactive browser walkthrough or hosted-service certification. Browser, Docker/Linux, production deployment and live providers remain AUD-044.

Broader campaign/currency/history truthfulness (AUD-037/047), review integrity (AUD-024), query performance (AUD-042), global lint (AUD-045) and remaining schema/release work (AUD-049) retain their original scope. The existing header/showcase native-image lint warnings are recorded separately; this task does not claim a clean repository-wide lint run.
