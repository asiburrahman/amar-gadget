# AUD-032 implementation notes (in progress)

Status: **implementation and local verification complete; production rollout not performed**. The final operator contract is in [Seller settlement runbook](SELLER_SETTLEMENT_RUNBOOK.md). These chronological notes preserve the approved scope and intermediate engineering decisions; earlier pending lists below describe their own checkpoints, not the final state.

## Approved operator rules

- The administrator configures commission percentages and whether shipping belongs to the seller or platform. There is no invented commission default.
- A shipment's earned funds become available immediately when it is delivered and payment is collected. COD uses that shipment's confirmed collection, even if another seller's shipment remains unpaid. Stripe uses verified order payment state.
- The administrator initiates a payout, sends money externally and confirms the actual payment method/reference. Creating a payout must not claim that money has been sent.
- Existing refund policy remains intact: full or item/quantity refunds; pre-dispatch shipping eligibility; post-dispatch shipping retained; stock only restored under the established inspected-return rules.

`SellerSettlementPolicy` is append-only, with sequential revisions per GLOBAL or SELLER scope. Terms specify commission in basis points (0 through 10,000) and the actual shipping recipient. A seller-specific revision can explicitly restore inheritance with null terms; this does not mean zero commission. Configured policies require a verified administrator; a seller scope must exist. The effective policy is the latest non-inheriting seller override, otherwise the latest global policy, otherwise unconfigured.

New fulfillment rows capture the effective immutable policy ID. A later setting change does not rewrite old purchases. Existing fulfillments are backfilled as LEGACY_UNCONFIGURED, and purchases made before configuration also retain null terms. Neither becomes payable using a new inferred rate. A reasoned, verified administrator may explicitly adopt reviewed terms once for an unconfigured shipment. Its original capture source/date remain fixed, while adoption stores actor, reason, UTC time and next revision. Once configured, its terms cannot be replaced. Snapshot and policy evidence cannot be deleted.

These are captured scalar shipment/order/seller identities; historical evidence is not silently cascaded away by deletion of an unrelated unpaid fixture. Subsequent financial ledger code must retain actual money postings and reconcile only existing matching order/shipment records, with explicit treatment of deletion/retention.

## Integer-paisa calculations

The TypeScript financial calculation uses BigInt and validates nonnegative, internally reconciled purchase amounts. Commission applies to remaining discount-adjusted goods, excludes shipping, and rounds half up once per shipment. Refunded goods therefore reverse the corresponding fee instead of paying commission on returned value.

For multi-seller orders, original post-discount goods allocate shipping proportionally, with stable ASCII shipment IDs breaking largest-remainder ties. If all goods were fully discounted, original gross goods supply the weights. Refunded shipping follows the captured original shipping shares; changing a seller's current catalog, commission or recipient does not redistribute the original purchase. Known provider losses are allocated across remaining goods/shipping before commission. Any loss exceeding the remaining allocated funds is exposed separately rather than hidden by a negative money clamp.

No terms or unreconciled purchase pricing produces an explicit policy/pricing hold. Active refunds, disputes and recorded financial/reservation review withdraw availability pending reconciliation. Lost provider funds reduce remaining entitlements using recorded amounts. Undelivered, uncollected or cancelled shipments do not produce available funds. The later ledger must record adjustments when these truths change; after an already completed payout, a refund/loss can create a seller receivable and must not be erased by clamping the wallet to zero.

## Mutation boundaries prepared for the next implementation step

Strict schemas cover global/seller policy changes, one-time adoption, payout initiation, external confirmation and cancellation. Every write requires a UUID, reason and affirmation. Terms and payout state decisions carry observed revisions. Actor identities and balances are not accepted from callers. Payout amounts are canonical integer-paisa strings, preserving aggregate values beyond JavaScript's safe integer limit. The UI percentage parser accepts up to two decimal places without floating-point rounding. Cancelling requires a separate declaration that no money was sent; confirming requires an external reference.

## Ledger and API progress, 3 November 2026

The ledger and service items above now have implementation and focused PostgreSQL evidence; AUD-032 remains open pending the user interface and final verification. Migrations 29 (`20261103100000_settlement_projection`), 30 (`20261103103000_settlement_partial_order_states`) and 31 (`20261103110000_seller_ledger_payouts`) were applied to newly isolated test databases and are frozen. Migration 30 preserves applied history while correcting the projection's aggregate-order state guard: a delivered/collected vendor can earn funds while the parent order is PARTIALLY_SHIPPED or PARTIALLY_DELIVERED. TypeScript now uses the existing canonical aggregate-state constants. No existing application/production database was migrated; readiness remains at the previous completed task's migration until final rollout preparation.

The PostgreSQL projection matches the TypeScript calculation for actual purchase rows, per-vendor delivery/collection, discounted refunds and provider-reconciled disputes. Its JSON money uses canonical decimal strings. Stable allocation and commission use exact numeric integer arithmetic. The native provider boundary is still a test fixture; source application behavior continues to use its actual configured provider.

Deferred order, item, fulfillment and term-adoption triggers project final transaction state into `SellerAccrual`. Actual changes post immutable `SellerLedgerEntry` adjustments, and `SellerWallet` balances must reconcile with those entries. Repeated reconciliation does not duplicate credit. Wallet balances may become negative after a paid-out purchase is refunded or lost; this is a seller receivable, and later earnings offset it. Holds withdraw availability and record subsequent restoration using actual remaining purchase amounts. Purchases/shipments with posted money cannot be deleted, and ledger, payout events and request receipts are retained. Zero-value removed sources retain a labelled zero projection.

Payout creation serializes against the current wallet, reserves a positive amount and records an unconfirmed instruction. Competing reservations cannot overspend. Confirmation records an actual external method/reference, normalized for duplicate detection, without another wallet debit. Cancellation requires an explicit declaration that no money was sent and releases the reservation exactly once. Confirmed/cancelled intents cannot be rewritten or re-resolved. Recording an external transfer remains possible if an intervening refund has created debt; it records actual money movement instead of hiding a payment that has already occurred.

`mutateSellerSettlement` verifies the current administrator/session under lock, requires strict observed revisions and persists exact UUID/hash receipts. One-time adoption locks Order before account/snapshot, then deferred posting locks wallets. Payout reservation does not acquire an order lock after its wallet, avoiding the reverse lock edge. `readSellerSettlement` uses a repeatable snapshot, verifies the current role/session, scopes members to themselves and exposes exact string amounts, separate payable/receivable totals, actual reservations/paid transfers, held/unconfigured shipments, captured/effective policies and a 12-month Asia/Dhaka posting history. Ledger, policies, shipments, payouts and administrator owner directories use real 20-record pages; totals are whole-scope aggregates. Admin request receipts remain scoped to their originating administrator even when filters change.

`/api/settlements` now provides private/no-store GET reads and administrator-only POST mutations, with the current viewer required in `X-Settlement-Owner`. Duplicate/unknown query fields, actor/balance injection, oversized JSON, missing affirmation and current-account mismatches fail explicitly. A provider/database failure never returns a successful financial result. This API does not send an external payout.
